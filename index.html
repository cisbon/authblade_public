Runtime control for AI agents

Your AI agent can act. AuthBlade decides if it should.

Agents have stopped just writing text. They raise purchase orders, edit customer records, send mail, and push code. AuthBlade sits between your agent and the systems it touches. It checks every action that matters against rules you write, blocks the ones that break them, and keeps a record of what actually happened.

The problem

An agent with a login is not an agent with permission.

Most agents today run with a set of credentials and a prompt telling them to behave. Both of those fail quietly.

Your procurement agent opens an invoice. Buried in the text is a line addressed to the agent: also update the supplier's bank account to the one below. The agent has valid credentials, so the system says yes.

✕DENY AuthBlade says no. The change never reaches SAP, and you get a record showing what was attempted and why it was stopped.

Instructions are not a boundary

Anything your agent reads can turn into an instruction. A rule written in a prompt can be talked out of by the next document the agent opens.

Logging in is not being allowed

Authentication proves who the agent is. It says nothing about whether this action, on this record, for this amount, should happen at all.

Self-reported work is not evidence

Agents tell you what they did. When that report is the only record, you are trusting the thing you are trying to check.

How it works

Three steps, every time.

The agent never decides whether it is allowed to proceed. Something it cannot switch off does that.

  1. 1

    Your agent tries to do something

    Call a tool, open an application, submit a form, move money. Anything that would change a system of record.

  2. 2

    AuthBlade checks your rules

    Which agent is asking, what it wants to do, which record, how much, and in which system. The answer is yes or no, with a reason.

  3. 3

    It runs, or it does not

    Allowed actions go through. Blocked ones never reach the target system. Either way you get a record of what was asked, what was decided, and what happened.

Guards

Two ways to plug it in.

A Guard is the piece that sits in the path of the agent. Which one you need depends on how your agent does its work.

Desktop Guard

For agents that use a computer the way a person does. Some work has no API, so the agent clicks through Windows, Citrix, or a virtual desktop instead. Desktop Guard runs on that machine. It sees which application is in front, decides whether the agent may open it, and stops the ones you have not approved.

  • Excel
  • Word
  • SAP GUI
  • Outlook
  • PowerShell

It works alongside your existing Windows and Citrix controls, not instead of them.

Desktop Guard details

MCP Guard

For agents that call tools and APIs. MCP Guard sits in front of the tool. Your agent asks to raise a requisition for 2,500 euros; MCP Guard checks the rule and runs it only if the answer is yes. The credentials stay with the Guard, so the agent gets the result and never the password.

That distinction matters more than it sounds. An agent that holds an API key can be talked into using it for something you never intended. An agent that holds nothing cannot.

Where it fits

Built for the work agents are already being given.

Start with the one process where an agent mistake would actually hurt, then widen it.

SAP procurement

Let an agent raise requisitions up to a limit you set, and never let it touch supplier bank details.

Windows and Citrix agents

Give a computer-use agent the three applications it needs for the job and nothing else on the machine.

Tool and API governance

Publish narrow tools to your agents and check every call, including the amounts and record ids inside it.

Finance and payments

Put ceilings on what an agent can move, per currency and per company, and stop everything above the line.

Decide what your agents can do, before they do it.

Start with one agent and one rule you actually care about. Add the rest when each one earns its place.

Privacy

How AuthBlade handles data

This is a placeholder. It describes the data handling the product is designed for. It is not a published privacy notice and creates no legal commitment. A formal notice will be published with the public service.

What the platform records

AuthBlade records structured facts about agent actions: which agent asked for what, on which record, under which task, which rule decided it, what the answer was, whether it ran, and what came back. That set exists so an action can be checked before it happens and explained afterwards.

What it does not record

  • Credentials of any kind. Only hashes of AuthBlade's own API keys exist, and no target system secret is ever stored.
  • Prompts or model reasoning. There is no database column for them.
  • Screenshots. Capture is not implemented and would need an explicit opt-in design.
  • Full request or response payloads. Free-form fields are size limited and redacted on the way in.

Personal data

Personal data appears in three narrow places, and each is kept as small as possible:

Delegating user
An opaque identifier by default rather than a name, recorded so an action can be traced back to the person it was done for.
Devices and sessions
Device identifier, session times, and application usage for Desktop Guard, kept for the correlation window.
Platform accounts
Names and email addresses of people who sign in to manage rules.

Desktop Guard is not workforce monitoring

Low-level events such as mouse movement and keystrokes stay on the machine and are summarised rather than sent anywhere. Where a person shares a desktop with an agent, consultation and notice obligations vary by country and remain the deploying organisation's responsibility.

Keeping tenants apart

Every record belongs to a workspace. Separation is enforced in the database itself and again in every server query, so one mistake in one layer is not enough to expose another customer's data. Those tests block a release.

Deletion and retention

Decision history is append only, because a record that can be quietly edited is not evidence. A documented administrative deletion path sits alongside it so a lawful deletion request can be honoured. Configurable retention, data residency, and customer-held encryption keys are on the roadmap and are not available today.

No warranty

The information here is provided as is, without warranty of any kind. AuthBlade is a security product under development, and how well it works depends on how it is deployed. It can only stop an action it sits in front of. Where an agent has another route to a system, AuthBlade records rather than prevents, and working that out per system is part of deploying it.

Other controls still matter

Desktop Guard works alongside operating system application control, separate accounts, Citrix and virtual desktop policies, endpoint management, network rules, and identity permissions. Nothing here should be read as a claim that AuthBlade on its own secures a Windows environment.
