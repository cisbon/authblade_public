Runtime authority and observability for AI agents

Product

Control, observe, and assure every AI agent action.

AuthBlade is a cross-channel runtime authority and observability platform. It evaluates proposed AI agent actions against deterministic policies, enforces decisions through trusted enforcement points, and records the chain from assigned task and authorization decision to actual execution and business outcome.

Problem

Agents moved from advice to execution. Authorization did not move with them.

What agents now do

  • Call APIs and MCP tools
  • Operate browsers and Windows desktops
  • Work through Citrix and virtual desktops
  • Use SAP GUI, Word, Excel, and enterprise applications
  • Read, create, modify, or delete records
  • Send communications and initiate transactions
  • Execute code and infrastructure changes
  • Delegate work to other agents and act for human users

How access is commonly granted

  • Broad credentials and shared service accounts
  • Human user sessions reused by automation
  • Authorization embedded in application code
  • Prompt instructions used as guardrails
  • Voluntary authorization checks the agent may skip
  • Unrestricted desktop, browser, or shell access
  • Incomplete or disconnected logs
  • Agent-reported execution outcomes

Prompts are not a security boundary. An instruction in context can be overridden by other context, including content the agent reads while working.

Authentication does not determine whether a specific action is permitted. Proving who the agent is says nothing about whether this action, on this resource, with these parameters, is allowed.

Bypass risk

Excessive permissions, missing or skipped checks, ignored denials, and unauthorized execution paths.

Credential risk

Reusable secrets reaching the model context, prompt-injection-driven actions, and credential misuse.

Evidence risk

A business black box: no reliable connection between authorization and execution, and insufficient audit evidence.

Organizations need pre-action control and post-action visibility, not one or the other.

How it works

The agent proposes. AuthBlade decides. A trusted enforcement point enforces.

AuthBlade is the Policy Decision Point. MCP Guard, Desktop Guard, Browser Guard, Code Guard, gateways, and brokers are Policy Enforcement Points. AuthBlade is preventive only when the agent cannot bypass the enforcement point.

  1. 1

    Agent receives a task

    The task, its purpose, constraints, and the delegating user are registered in the Control Plane.

  2. 2

    Agent proposes an action

    A tool call, an application launch, a form submission, or a transaction.

  3. 3

    A trusted enforcement point intercepts it

    The enforcement point authenticates with its own identity and normalizes the request into the canonical action model.

  4. 4

    AuthBlade evaluates policy

    Deterministic attribute-based evaluation against a specific policy version. Default DENY. Explicit DENY overrides ALLOW.

  5. 5

    Enforcement allows or blocks

    On DENY, execution does not start. On ALLOW, the trusted component executes with credentials the agent never sees.

  6. 6

    Result is recorded

    Execution status and outcome are written with an evidence source and evidence level.

  7. 7

    One timeline

    Task, decision, action, and outcome appear together, correlated by shared identifiers.

The agent does not control

  • Whether AuthBlade is called
  • Whether DENY is respected
  • Whether credentials are exposed
  • Whether execution occurs
  • Whether outcomes are recorded
  • Whether human approval is required

Architecture

A shared control plane with channel-specific enforcement.

One authority model, one canonical action model, and one evidence chain. Each channel keeps its own enforcement component because no single integration can govern every agent type.

Enforcement flow

An AI agent proposes an action to an enforcement point, which is MCP Guard, Desktop Guard, Browser Guard, or Code Guard. The enforcement point sends a normalized authorization request to the AuthBlade Control Plane, which contains an authority layer, an evaluation and approval layer, and an observability layer. The Control Plane returns ALLOW or DENY. Only after ALLOW does the enforcement point let the target system execute. The target system reports the outcome back into the action chain.

AuthBlade Desktop Guard Defined component

Govern computer-use agents across Windows, Citrix, and virtual desktops.

Desktop Guard is an AuthBlade enforcement component for computer-use agents operating Windows, Citrix, virtual desktops, Cloud PCs, and enterprise GUI applications. It creates a trusted enforcement layer between the computer-use agent and the desktop environment.

Computer-use agent → Desktop Guard → AuthBlade Control Plane → Controlled Windows, Citrix, or virtual desktop

What Desktop Guard does

  • Registers devices and sessions with their own identity
  • Identifies the agent and the enforcement point separately
  • Detects the active process, application, and foreground window
  • Uses Windows UI Automation context where available
  • Evaluates application launches
  • Evaluates consequential desktop actions
  • Applies session restrictions
  • Prevents denied input or execution
  • Records actions, decisions, and outcomes
  • Supports local policy information for low-latency interactions
  • Fails closed for protected actions
  • Resists agent-driven disablement
  • Avoids arbitrary process or shell access
  • Integrates with Windows and Citrix controls

Scope today and next

Initial implementation Device and session registration, process and application identification, application allow and deny, event logging, timeline integration.

Next phase Deep UI Automation, business-action recognition, SAP adapters, screen-state verification, consequential-button interception, advanced local decisions, cryptographic evidence, Citrix integration, advanced tamper resistance.

Desktop Guard complements, it does not replace

Windows App Control, AppLocker, account separation, Citrix policies, VM isolation, endpoint management, network restrictions, mailbox entitlements, and Microsoft Graph permissions remain necessary. AuthBlade alone does not prevent every Windows action without supporting operating system and environment controls. Desktop Guard adds an agent-aware authorization and evidence layer on top of those controls.

AuthBlade MCP Guard

Authorize structured tool calls without exposing credentials.

The agent receives a business capability. The trusted MCP server keeps the credential. AuthBlade evaluates the action and its parameters, and execution happens only after ALLOW.

  1. Agent invokes a narrowly defined tool.
  2. MCP Guard authenticates and identifies the agent and enforcement point.
  3. MCP Guard sends a normalized authorization request.
  4. AuthBlade returns ALLOW or DENY.
  5. DENY stops execution.
  6. ALLOW lets the trusted MCP server execute.
  7. Credentials remain inside the trusted server.
  8. The server reports execution and outcome.
  9. AuthBlade adds all events to the shared timeline.

Observability

Illuminate the agent execution black box.

AuthBlade records the authority and execution chain: task, delegation, proposed action, policy, decision, enforcement, actual action, and outcome. Records are structured metadata, not hidden model reasoning.

Task chain

Purpose, constraints, delegating user, parent task, child tasks, related sessions and traces.

Decision chain

Proposed action, resource, context, policies evaluated, matching policy version, decision, reason code, latency.

Action chain

Action level, application or target, safe input metadata, status, start and end times, parent action, external reference.

Outcome chain

Execution status, external reference, safe result metadata, execution and reporting times, evidence source and level.

AGENT_DECLARED

The agent claims it attempted or completed the action. Lowest confidence.

ENFORCEMENT_OBSERVED

A trusted Guard or enforcement component observed or executed the action. Higher confidence.

TARGET_CONFIRMED

The target system confirms the action. Highest confidence.

Decision-to-action matching

Every action carries a match status so that a reviewer can see whether execution corresponded to an authorization.

  • MATCHED
  • UNMATCHED
  • NOT_EXECUTED
  • UNKNOWN

The MVP stores and displays the status. Semantic matching is designed as an ActionMatcher extension and is not implemented.

Mismatches the model is designed to surface

  • Execution without a decision
  • Execution after DENY
  • A different resource or different parameters
  • Expired authorization
  • Duplicate execution
  • Authorized but not executed
  • Outcome without enforcement evidence

AuthBlade produces an audit-ready action chain. It does not claim tamper-proof evidence, because cryptographic and target-confirmed evidence is a later phase.

Action levels

Not every interaction deserves a cloud round trip.

Interaction

Low-level event: mouse movement, click, keystroke, scroll, focus, low-level API interaction.

Desktop Guard may evaluate low-risk interactions locally using a signed, expiring session policy.

Operation

Meaningful technical action: open application, read file, update record, invoke MCP tool, submit form, upload or download, start session.

Operations are authorized and observed where relevant.

Business action

Consequential event: create purchase requisition, submit payment, change supplier bank details, send external email, post journal entry, approve invoice, modify production.

Business actions normally require central evaluation and may later require human approval.

Security

Security properties the design depends on.

The agent is not trusted to enforce permission

Enforcement lives in a component the agent cannot disable, bypass, or instruct.

Credentials remain outside the model

Trusted components hold secrets. The agent receives capabilities and results.

Decisions are deterministic

The same input and the same policy version always produce the same decision.

Protected actions fail closed

Timeout, error, or unavailability means the action does not execute. The MVP has no fail-open mode.

Explicit DENY overrides ALLOW

Default DENY applies to anything unmatched. Inactive agents and invalid requests are denied.

Agent and enforcement-point identities are separate

Each enforcement point registers and authenticates with its own credential, and AuthBlade verifies that it may represent the claimed agent and channel.

Historical snapshots are preserved

Decisions store an immutable snapshot of the request and the policy version that produced them.

Secrets are excluded from logs

Payloads are limited and redacted. Screenshots are not captured by default.

Actions, not reasoning

AuthBlade records structured actions and outcomes, not prompts or hidden model reasoning.

Desktop Guard complements operating system security

App Control, AppLocker, account separation, Citrix policies, endpoint management, and network controls remain part of the boundary.

What this design does not defend against

Stated plainly, because an overclaimed boundary is itself a risk.

A human insider

Someone with legitimate access to the target system is outside the agent authorization boundary.

An operating system compromise

An attacker at or above the privilege of the Desktop Guard native helper.

A path with no enforcement point

If a target system accepts changes through a route that bypasses a Guard, AuthBlade records rather than prevents.

Harm from a permitted action

An action that policy legitimately allows can still be a bad business decision. Risk evaluation and approval are planned, not present.

AuthBlade does not claim certifications or legal compliance. Its evidence is an audit-ready action chain, not tamper-proof proof, because cryptographic and target-confirmed evidence is a later phase. See how data is handled.

Platform and implementation

Built on Node.js, React, Electron, and Supabase.

The control plane is a Node and TypeScript service over Supabase PostgreSQL. The administration interface is React. Desktop Guard is an Electron application paired with a native Windows helper, because an ordinary Electron renderer cannot block a Windows process on its own.

Supporting endpoints

  • POST /api/v1/tasksCreate a task with purpose, constraints, and delegating user.
  • GET /api/v1/tasks/{task_id}Read a task with its correlated sessions, decisions, actions, and outcomes.
  • POST /api/v1/tasks/{task_id}/eventsAppend task-level events such as start, checkpoint, and completion.
  • POST /api/v1/actionsRecord a started or completed action.
  • PATCH /api/v1/actions/{action_id}Update status, end time, result reference, or error.
  • POST /api/v1/decisions/{decision_id}/outcomeRecord the outcome bound to a decision.
  • POST /api/v1/sessionsOpen a session and, for Desktop Guard, receive a signed session policy.
  • POST /api/v1/sessions/{session_id}/endClose a session and invalidate its session policy.
  • POST /api/v1/enforcement-points/registerRegister an enforcement point and issue its credential.
  • POST /api/v1/devices/registerRegister a device for Desktop Guard credential binding.

Workspace isolation in the database

Row Level Security on every tenant table, plus an explicit workspace filter in every server query. Two independent mechanisms, so one mistake is not enough to cross tenants.

Immutable snapshots

A decision stores the evaluated request and the exact policy version that produced it, so it stays explainable after the policy changes.

Hashed credentials only

API keys and enforcement-point credentials are stored as hashes. The secret is shown once at issue.

No column for prompts

There is no field for prompts, reasoning, or screenshots. A structural absence is stronger than a rule against writing.

What the platform records

AuthBlade records structured metadata about agent actions: which agent proposed what action, on which resource, under which task, which policy version decided it, what the decision was, whether execution followed, and what the result was. That set exists so an action can be authorized and later explained.

What it does not record

  • Credentials of any kind. Only hashes of AuthBlade's own API keys exist, and no target system secret is ever stored.
  • Prompts, hidden model reasoning, or chain-of-thought. There is no database column for them.
  • Screenshots. Capture is not implemented and would require an explicit opt-in design.
  • Full request or response payloads. Free-form fields are size limited and redacted at ingestion.

Personal data

Personal data appears in three narrow places, and each is minimized by design:

Delegating user
An opaque identifier by default rather than a name, recorded so an action can be traced to the person on whose behalf it happened.
Devices and sessions
Device identifier, session times, and application usage for Desktop Guard, retained for the correlation window.
Platform accounts
Names and email addresses of people who sign in to the control plane.

Desktop Guard is not workforce monitoring

Interaction-level events such as mouse movement and keystrokes are deliberately kept local and aggregated rather than sent to the control plane. Where a person shares a desktop with an agent, worker consultation and notice obligations vary by jurisdiction and remain the deploying organization's responsibility.

Tenant isolation

Every tenant record carries a workspace identifier. Isolation is enforced by Row Level Security in the database and by an explicit workspace filter in every server query, so a single mistake in one layer is not sufficient to expose another tenant's data. Isolation tests are a release blocker.

Deletion and retention

Decision and outcome history is append only, because an audit chain that can be quietly edited is not evidence. A documented administrative deletion path exists alongside it so that a lawful deletion request can be honoured. Configurable retention, data residency options, and customer-managed encryption keys are on the roadmap and are not available today.

This website

What this website is

An informational page describing AuthBlade, a cross-channel runtime authority and observability platform for AI agents. It offers no account, no sign-up, no purchase, and no hosted service. Nothing on it forms a contract or an offer.

  • Anything marked as planned or long term is not available and must not be relied upon in a purchasing or architectural decision.
  • All decision records, timelines, policies, and identifiers shown are illustrative examples, not data from a running system.
  • No certification, audit outcome, or legal compliance is claimed anywhere on this page.

No warranty

The information here is provided as is, without warranty of any kind. AuthBlade is a security product under development, and its security properties depend on deployment. In particular, AuthBlade prevents an action only where the agent cannot reach the target system without crossing an enforcement point. Where it can, AuthBlade records rather than prevents. Assessing that per channel is part of deploying it.

Complementary controls remain necessary

Desktop Guard complements, and does not replace, operating system application control, account separation, virtual desktop and Citrix policies, endpoint management, network restrictions, and identity permissions. Nothing on this page should be read as a claim that AuthBlade alone secures a Windows environment.
